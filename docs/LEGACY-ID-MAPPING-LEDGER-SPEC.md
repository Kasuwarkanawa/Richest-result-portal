# Legacy ID Mapping Ledger — Review Specification

**Status:** Proposal only. This document does not create or alter database objects.
**Scope:** `RIGCHEST-RESULT-PORTAL` migration branch only.
**Production rule:** MongoDB remains the active production identity store. No cutover or import is authorized by this specification.

## 1. Purpose

Maintain an auditable, one-to-one mapping from each source MongoDB ObjectId to its target PostgreSQL UUID. A target UUID must never be inferred by casting, truncating, or parsing an ObjectId. Runtime consumers may resolve only ledger entries whose status is `verified`.

## 2. Proposed ledger record

| Field | Type (proposed) | Requirement |
|---|---|---|
| id | uuid | Primary key generated by PostgreSQL |
| source_system | text | Stable source identifier, e.g. `mongodb-rigchest` |
| entity_type | text | Allowlisted entity name: users, students, departments, programs, regulations, batches, semesters, subjects, exam_sessions, exam_registrations, mark_entries, grading_policies, processed_results, semester_summaries, publish_snapshots |
| legacy_id | text | Exactly 24 hexadecimal characters, stored lowercase |
| target_id | uuid | Target PostgreSQL UUID |
| mapping_status | text | pending, imported, verified, rejected |
| migration_batch_id | uuid | Batch that produced or checked this mapping |
| source_checksum | text | SHA-256 of canonical source record |
| target_checksum | text | SHA-256 of canonical target record after import |
| verified_at | timestamptz | Required when status is verified |
| verified_by | uuid | Authorized migration operator, where available |
| created_at / updated_at | timestamptz | Audit timestamps |

Do not store passwords, PINs, access tokens, or other credential material in this ledger.

## 3. Integrity constraints

The eventual reviewed DDL should enforce:

1. Unique `(source_system, entity_type, legacy_id)`: one source identity has one mapping.
2. Unique `(source_system, entity_type, target_id)`: no two source identities of the same entity map to one target.
3. Check `legacy_id` against `^[0-9a-f]{24}$`.
4. Check `mapping_status` against the four documented states.
5. `verified_at` must be non-null exactly when status is `verified`.
6. `source_checksum` and `target_checksum` must be valid 64-character lowercase SHA-256 hex values before verification.
7. Foreign keys to a migration-batch table only after that table and its lifecycle are separately reviewed.

A cross-entity collision is not automatically a conflict because UUID identity is scoped by entity; however, target UUIDs should also be checked against the actual target table's primary key during reconciliation.

## 4. State transitions

- `pending` → `imported`: target row inserted and its target UUID recorded.
- `imported` → `verified`: source/target counts and canonical checksums match; all required foreign keys resolve.
- `pending` or `imported` → `rejected`: a discrepancy is recorded and the batch is stopped for review.
- `verified` is immutable for normal import jobs. Corrections require an explicit, separately audited remediation; never silently overwrite a verified mapping.

## 5. Reconciliation gates per batch

Before marking any row verified, produce a report containing:

- Source and target row counts grouped by entity type.
- Missing source IDs, missing target IDs, duplicate mappings, and duplicate target IDs.
- Source and target checksum mismatches.
- Orphaned foreign keys for all migrated relationships.
- Credential-preservation checks that confirm hashes are present and unchanged without printing the hashes.
- Snapshot/result record counts and checksum comparisons for historical published results.
- A batch-level manifest checksum and an operator approval record.

The batch fails closed if any unexplained mismatch exists. Do not use a percentage threshold to waive missing identities or result/snapshot discrepancies.

## 6. Security and access

- Keep RLS enabled.
- Do not grant `anon` or `authenticated` access.
- Keep ledger writes and reads in a server-only migration process using a privileged credential stored only in server environment variables.
- Do not return mapping ledger contents from public API routes.
- Record operator and batch metadata, not secrets.
- Never log raw credentials or full student personal records in reconciliation output.

## 7. UUID generation policy

The isolated helper generates deterministic UUIDv5 candidates using a fixed, reviewed namespace and the UTF-8 bytes of a JSON-encoded tuple `[source_system, entity_type, legacy_id]`. This unambiguous tuple encoding prevents delimiter-boundary collisions. The generated value is a candidate only: persist it once in the ledger, check target-table collisions, and thereafter reuse the ledger value. Changing the namespace or tuple format after import begins is prohibited without a versioned migration plan.

The helper must never be treated as a substitute for the ledger. Missing, duplicate, malformed, or unverified mappings must stop the import.

## 8. Explicitly out of scope

This proposal does not:
- execute SQL or create tables, indexes, triggers, policies, or grants;
- import or update any Supabase records;
- change authentication, JWT claims, or actor IDs;
- change MongoDB or production;
- authorize merging PR #3 or performing cutover.

## 9. Approval required before implementation

Review the allowlisted entity types, retention/audit requirements, namespace ownership, batch lifecycle, and operator authorization model. Only after approval should a separate schema migration be authored, reviewed, applied to the non-production Supabase project, and tested with synthetic records.
